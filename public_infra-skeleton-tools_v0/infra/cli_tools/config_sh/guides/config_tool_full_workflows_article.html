Config Tool Workflows

A practical guide to using the config tool as a daily research, development, and publishing system: manage role accounts from the operator seat, work inside the right target identity, use lv as the Python environment cockpit, promote packages deliberately, run one managed step at a time, and keep research, engineering, and writing work separated without making the system hard to use.

Abstract. The config tool is a role-aware workstation control plane. It helps one operator prepare several target identities such as aiengineer, researchscientist, and publisher. The tool is useful because it separates four things that are easy to mix up during real work: who is being configured, which Python environment receives packages, which shares and credentials are allowed, and which setup steps have already run. This article starts with the everyday feeling of using the tool, then moves into concrete workflows for package decisions, managed installers, five-node gene regulatory network model development, parameter search, training and inference, remote infrastructure preparation, OpenClaw-assisted thinking over a personal knowledge base, and LaTeX paper production.

1. The reader journey: what the tool should feel like

Scenario. You are not trying to admire a clever shell script. You are trying to get research and development done without losing track of which user owns the files, which environment contains the packages, which share contains sensitive material, and which setup commands have already changed the machine.

The tool should feel like a careful laboratory assistant. It should not hide decisions from you, but it should also not force you to remember every low-level command. It should let you inspect first, change one thing, verify the result, then continue your actual work. That is why the workflow starts gently: check the target, inspect the Python environments with lv, decide whether a package belongs in a temporary experiment or a repeatable role stack, then run one managed setup step.

The tone of use. The tool is strongest when it stays boring: inspect, decide, run one precise action, verify. The power comes from doing that consistently across research, AI engineering, and publishing roles.

2. The mental model: prepare the bench, sit at the bench

The simplest way to understand the tool is this: config --target USER ... prepares a workbench from the outside, and su - USER lets you sit at that workbench. The operator account is the person who prepares accounts, mounts, policies, setup steps, and shared resources. The target account is the identity that actually performs research, development, writing, and publication work.

This model matters because it answers the practical question that comes up every day: “Should I run this as the operator, or should I become the target user?” When you are changing setup, use config --target. When you are doing the work itself, become the target user.

3. The daily loop

Most sessions should follow the same rhythm. First, check what role you are working on. Second, inspect the environment landscape. Third, decide whether this is a setup action or real research work. Fourth, make the smallest possible managed change. Fifth, verify that the result helps the work. 

# Inspect the role from the operator seat.
config --target researchscientist config-show
sudo config --target researchscientist bootstrap status
config --target researchscientist bootstrap steps

# Inspect Python environments with lv.
lv
lv conda researchscientist

# Run one specific managed setup step only when needed.
sudo config --target researchscientist bootstrap step install_grn_research_python_stack

# Verify again.
lv conda researchscientist
sudo config --target researchscientist bootstrap status
How this helps the work. This loop prevents the two most common mistakes: installing packages into the wrong Python environment, and running broad setup when you only meant to prepare one missing capability.

4. Scenario: manage a role from outside, work inside the role

Scenario. You are moving between three types of activity: managing the account, developing or researching inside the account, and publishing from a separate writing identity. The tool should make that distinction visible instead of letting everything happen as one user.

When to use config --target

Use config --target USER ... when you are preparing or repairing the target role from the operator seat. This is where you create or reconcile accounts, inspect target policy, prepare mounts, create credential files, run managed setup steps, reset skipped state, and check what has already run. 

# Prepare the research scientist role from the operator seat.
config --target researchscientist config-show
sudo config --target researchscientist bootstrap status
config --target researchscientist bootstrap steps
sudo config --target researchscientist credentials per-share
sudo config --target researchscientist mount
sudo config --target researchscientist bootstrap step install_grn_research_python_stack
What this does for research. You are preparing the research bench: policy, mounts, credentials, and scientific tooling. You are not yet writing notebooks or running simulations. The setup is controlled and recorded before the research account starts producing files.

When to use su - targetname

Use su - USER when the setup is ready and you want to work as that identity. That is when you edit notebooks, run scripts, inspect model output, start local servers, write the paper, or open the personal knowledge base. The target user should own the files created during that work. 

# Become the research identity for actual research work.
su - researchscientist
lv
lv conda grn-5node-prototype
cd ~/projects/grn-5node
conda run -n grn-5node-prototype jupyter lab --no-browser
What this does for research. Now the notebooks, figures, logs, and intermediate outputs belong to the research scientist role. This keeps research work separate from operator maintenance and from publisher draft production.

The same split for engineering and publishing

# Prepare the AI engineering bench.
config --target aiengineer config-show
sudo config --target aiengineer bootstrap step install_llm_stack
sudo config --target aiengineer bootstrap step install_api_stack
sudo config --target aiengineer bootstrap step check_docker_access

# Then work as the AI engineer.
su - aiengineer
lv conda aiengineer
cd ~/projects/model-service
conda run -n aiengineer python -m uvicorn app:app --reload
# Prepare the publishing bench.
config --target publisher config-show
sudo config --target publisher bootstrap step install_publisher_base_tools
sudo config --target publisher bootstrap step install_publisher_notebook_stack
sudo config --target publisher bootstrap step install_pandoc_obsidian_tools
sudo config --target publisher mount

# Then work as the publisher.
su - publisher
lv conda publisher
cd ~/writing/grn-paper
pandoc manuscript.md -o draft.tex
Rule of thumb. Use config --target when changing setup. Use su - USER when creating real work artifacts. When work reveals a missing dependency, do not patch it casually from the target shell. Decide whether it belongs in a temporary environment or in stable package policy.

5. Scenario: choose a package, enter it, and understand where it lands

Scenario. You discover a package that may help with a five-node gene regulatory network model, a parameter search workflow, local model inference, API serving, or paper export. Before adding it, you need to decide whether it is experimental or stable role policy.

Start with the question the package answers

Do not start by asking “how do I install this?” Start by asking what problem the package solves. A numerical solver may belong to research. A hyperparameter search library may belong to optimisation. A local-model package may belong to AI engineering. A notebook export package may belong to publishing. The package should enter the stack that matches the work it supports.

  1. What problem does it solve? Simulation, plotting, parameter search, inference, API serving, publishing, or writing?
  2. Who needs it repeatedly? Research scientist, AI engineer, publisher, or only one temporary experiment?
  3. Where should it land? A named conda environment managed with lv.
  4. Should it become policy? Only after it proves useful in a prototype or experiment.

Verify the package name before adding it

The package name used by pip is not always the same as the import name used by Python. Check both in a throwaway or prototype environment before promoting the dependency into a stable stack. 

# Work inside the target identity for exploration.
su - researchscientist

# Use lv to create or inspect a prototype environment.
lv conda grn-5node-prototype -new
lv conda grn-5node-prototype

# Try the package in the prototype env before promoting it.
conda run -n grn-5node-prototype python -m pip install optuna
conda run -n grn-5node-prototype python -c "import optuna; print(optuna.__version__)"
What this does for research. The package is tested inside a named environment, not added directly to the stable role stack. This gives you freedom to try tools without turning every experiment into permanent policy.

Where you enter stable package policy

When a package proves useful and should become repeatable, enter it in the package policy file. This file is a recipe. Editing it does not install anything immediately; it changes what the matching managed installer will install later. 

sudoedit /home/vmuser/.local/etc/config-sh/install/packages.env
# Research scientist stacks
PIP_RESEARCH_NUMERIC_STACK="numpy pandas scipy matplotlib seaborn scikit-learn sympy"
PIP_RESEARCH_OPTIMIZATION_STACK="optuna scikit-optimize deap SALib"
PIP_RESEARCH_NOTEBOOK_STACK="ipython jupyter ipykernel nbconvert"

# AI engineer stacks
PIP_ML_BASE_STACK="numpy pandas matplotlib seaborn scikit-learn"
PIP_PYTORCH_STACK="torch torchvision torchaudio"
PIP_LLM_STACK="transformers accelerate datasets peft bitsandbytes"
PIP_API_STACK="fastapi uvicorn"
PIP_ML_DEV_TOOLS="rich typer ipython jupyter pytest"

# Publisher stacks
PIP_PUBLISHER_BASE_STACK="jupyter nbconvert matplotlib pandas"
PIP_PUBLISHER_NOTEBOOK_STACK="jupyterlab notebook nbconvert ipykernel"

What happens after you save the package

Nothing installs at save time. Later, when you run a managed step, the tool loads the package policy, chooses the target user, resolves that target's Python environment, calls the trusted installer function, and installs the package list into the resolved environment. Afterward, you inspect with lv.

6. Scenario: understand, change, or create a managed step

Scenario. You keep seeing commands such as bootstrap step install_grn_research_python_stack. You need to know what that step really is, where the installer lives, how the package list is connected, and how you would create or change one safely.

A managed step is not magic. It is a named action that connects a user-facing step name to a trusted shell function. That function may read a package list and install into the resolved Python environment. The tool keeps these pieces separate so that editable policy files cannot execute arbitrary shell commands.

Where the pieces are found

When you run a step, these are the places to inspect. The point is not to memorise them; the point is to understand the path from a friendly command to the actual work it performs.

PieceWhere it livesPlain-language meaning
Package list/home/vmuser/.local/etc/config-sh/install/packages.envThe recipe: which packages should this role stack contain?
Installer function/home/vmuser/.local/lib/config-sh/installers.shThe worker: what shell function actually installs or checks something?
Step registry/home/vmuser/.local/etc/config-sh/bootstrap/steps.tsvThe menu: which friendly step names exist?
Dispatch allowlist/home/vmuser/.local/bin/config.shThe safety gate: which functions are trusted enough to be called from a step?
Role plan/home/vmuser/.local/etc/config-sh/bootstrap/profiles/*.planThe default role choice: should this step start pending or skipped for this role?

Trace an existing research step

# Find the user-facing step.
grep -n 'install_grn_research_python_stack' /home/vmuser/.local/etc/config-sh/bootstrap/steps.tsv

# Find the actual function that does the work.
grep -n 'InstallGRNResearchPythonStack' /home/vmuser/.local/lib/config-sh/installers.sh

# Check that the function is allowed to be dispatched.
grep -n 'InstallGRNResearchPythonStack' /home/vmuser/.local/bin/config.sh

# See which role profiles include it.
grep -n 'install_grn_research_python_stack' /home/vmuser/.local/etc/config-sh/bootstrap/profiles/*.plan

# See which package variables feed the function.
grep -n 'PIP_RESEARCH_NUMERIC_STACK\|PIP_RESEARCH_OPTIMIZATION_STACK\|PIP_RESEARCH_NOTEBOOK_STACK' /home/vmuser/.local/etc/config-sh/install/packages.env
What this does for research. This tells you exactly why the GRN setup step exists, what it will run, what package recipes it can read, and which roles are allowed to receive it by default. You can change the recipe without changing the installer, or change the installer only when the behavior itself must change.

Create a new step only when the work is repeatable

A new step is useful when you have discovered a repeated action: for example, installing a GRN analysis add-on, preparing a Runpod client package set, checking a local model workspace, or validating a paper export toolchain. Do not create a new step for a one-off experiment. Use a prototype environment for that.

Example: add a future research visualisation step

# 1. Add a package recipe if the step installs packages.
sudoedit /home/vmuser/.local/etc/config-sh/install/packages.env
# Example:
# PIP_RESEARCH_VISUALIZATION_STACK="plotly bokeh networkx"

# 2. Add the trusted function.
sudoedit /home/vmuser/.local/lib/config-sh/installers.sh
# Example function name:
# InstallResearchVisualizationStack

# 3. Add the step registry row.
sudoedit /home/vmuser/.local/etc/config-sh/bootstrap/steps.tsv
# Example row:
# install_research_visualization_stackInstallResearchVisualizationStacktarget1Install research visualization Python stack

# 4. Allow the function in the dispatch gate.
sudoedit /home/vmuser/.local/bin/config.sh
# Add InstallResearchVisualizationStack to the trusted bootstrap function allowlist.

# 5. Decide which roles receive it by default.
sudoedit /home/vmuser/.local/etc/config-sh/bootstrap/profiles/research-scientist.plan
# Example:
# pending install_research_visualization_stack

Validate the new step before using it for real work

bash --noprofile --norc -n /home/vmuser/.local/bin/config.sh
bash --noprofile --norc -n /home/vmuser/.local/lib/config-sh/installers.sh
config --target researchscientist bootstrap steps | grep 'install_research_visualization_stack'
sudo config --target researchscientist bootstrap step install_research_visualization_stack
su - researchscientist
lv conda researchscientist
The useful distinction. Changing a package list changes what an existing step installs. Creating a new step changes what the tool knows how to do. Start with package policy when the behavior already exists. Add a new step only when you need a new repeatable action.

7. Scenario: use lv as the Python environment cockpit

Scenario. You are about to create, clone, inspect, or delete a Python environment. You should not reach first for raw conda commands unless you need something unusual. Use lv because that is what it was built for.

lv gives you a compact dashboard and direct environment operations. It can inspect aliases, conda environments, and virtual environments. It can create and delete environments. It can also clone an existing conda or virtual environment into a new target environment with selected packages. 

lv                         # dashboard
lv -help                   # help
lv conda researchscientist # inspect conda env
lv venv reports            # inspect virtualenv
lv conda grn-5node-prototype -new
lv conda grn-5node-prototype -del
lv conda researchscientist --clone --target conda grn-search-a --packages -python -pip -optuna -networkx
How this helps research and development. lv lets you see what environments exist before you run setup. It makes environment creation and cloning intentional. That is especially important when you need a stable research environment, one or more experimental search environments, and a separate AI engineering environment for services and inference.
Important boundary. lv manages and inspects Python environments. config prepares accounts, policy, mounts, and managed setup steps. Use them together: create or inspect with lv, point target policy at the intended environment, then run one managed step with config --target.

8. Role map: research scientist, AI engineer, publisher

The roles are not labels for decoration. They keep different kinds of work from contaminating each other. The research scientist role should be comfortable for model discovery, notebooks, numerical experiments, and parameter search. The AI engineer role should be comfortable for local models, APIs, inference services, and infrastructure checks. The publisher role should be comfortable for Obsidian-connected writing, notebook export, Pandoc, and LaTeX draft production.

Research scientist

Use this role for scientific modelling, five-node GRN experiments, parameter search, notebook analysis, figures, and reproducible research outputs.

AI engineer

Use this role for model-serving code, local inference tooling, API prototypes, Docker/Terraform/Kubernetes checks, OpenClaw checks, and remote-compute preparation.

Publisher

Use this role for writing, notebook conversion, Obsidian or personal knowledge base access, LaTeX drafting, figures, manuscript export, and final document assembly.

9. Scenario: five-node GRN Turing-capable model discovery

Scenario. You want to discover and develop a five-node gene regulatory network model that can produce Turing-capable behaviour. You need a first prototype, a numerical environment, notebook tooling, parameter search, and a disciplined path from idea to reproducible result.

Prepare the research bench from outside

Before writing model code, prepare the target. This makes sure package installation, environment selection, mounts, and state belong to the research scientist role. 

config --target researchscientist config-show
sudo config --target researchscientist bootstrap status
config --target researchscientist bootstrap steps
sudo config --target researchscientist bootstrap step install_grn_research_python_stack
Installer groundwork. The command uses the step install_grn_research_python_stack. That step is listed in bootstrap/steps.tsv, mapped to the trusted function InstallGRNResearchPythonStack in installers.sh, allowed by config.sh, and enabled for the research scientist profile. The function installs the numerical, optimisation, and notebook package stacks into the resolved research Python environment.

Create a prototype environment with lv

su - researchscientist
lv
lv conda grn-5node-prototype -new
lv conda grn-5node-prototype
mkdir -p ~/projects/grn-5node
cd ~/projects/grn-5node
How this helps discovery. The prototype environment gives you a safe place to explore equations, graph structures, activation and inhibition relationships, diffusion assumptions, parameter ranges, and plotting without polluting the stable research environment.

Start with the minimum useful model

A first prototype should be small enough to understand. Start with state variables, a reaction term, a diffusion term if needed, and a simple way to score whether the output shows useful spatial or temporal structure. Only then add heavier search or training machinery. 

conda run -n grn-5node-prototype python - <<'PY'
import numpy as np
print('prototype ready:', np.__version__)
PY

10. Scenario: refinement, training, inference, and parameter search

Scenario. The prototype runs. Now you need parameter search, hyperparameter tracking, inference scripts, and possibly model-training infrastructure. This is where the role split becomes useful: research scientist for scientific exploration, AI engineer for services and inference infrastructure.

Parameter search as research scientist

Use the research scientist role when the question is scientific: which parameter ranges produce a stable pattern, which network topology is promising, which perturbations preserve behaviour, and which plots explain the result. 

# From the operator seat, ensure the research search stack exists.
sudo config --target researchscientist bootstrap step install_parameter_search_tooling

# Then work inside the research role.
su - researchscientist
lv conda grn-5node-prototype
cd ~/projects/grn-5node
conda run -n grn-5node-prototype python scripts/search_parameters.py
Installer groundwork. The step install_parameter_search_tooling is the user-facing action for optimisation and sensitivity tools. It reads the research optimisation package stack from package policy and calls a trusted installer function through the bootstrap dispatch path. This helps the research because parameter-search dependencies become repeatable instead of hidden in one notebook's install history.

Inference and service work as AI engineer

Use the AI engineer role when the question becomes software delivery: wrapping a trained or selected model, exposing an API, testing inference latency, preparing a local model service, or checking infrastructure assumptions. 

# Prepare AI engineering dependencies from the operator seat.
sudo config --target aiengineer bootstrap step install_ml_base_python_stack
sudo config --target aiengineer bootstrap step install_pytorch_stack
sudo config --target aiengineer bootstrap step install_api_stack

# Then work inside the AI engineer role.
su - aiengineer
lv conda aiengineer
cd ~/projects/grn-inference-service
conda run -n aiengineer python -m uvicorn app:app --reload
Installer groundwork. These steps connect to separate package recipes: machine-learning basics, PyTorch, and API tooling. The separation is useful because you can update the service/API stack without forcing those packages into the research scientist's experiment environment.

Keep a clean promotion path

A package or script starts in a prototype. If it helps scientific discovery, promote it to the research stack. If it helps serving, inference, or infrastructure, promote it to the AI engineer stack. If it helps explain or export the result, promote it to the publisher stack.

11. Scenario: preparing remote compute and infrastructure

Scenario. Local experiments become too heavy. You want to prepare for Runpod or another remote compute target without mixing provider tokens, private credentials, and local notebooks into the wrong places.

Use the AI engineer role for the local side of remote-compute preparation: packaging code, checking Docker access, checking Terraform availability, checking Kubernetes context, and preparing API or inference wrappers. The config tool should not pretend to manage a remote provider unless you have a real managed step for that provider. 

config --target aiengineer config-show
sudo config --target aiengineer bootstrap step check_docker_access
sudo config --target aiengineer bootstrap step check_terraform_installation
sudo config --target aiengineer bootstrap step check_kubernetes_access

su - aiengineer
lv conda aiengineer
cd ~/projects/grn-runpod-worker
Installer groundwork. These are check steps, not install steps. They live in the same step registry and trusted-function path, but they should not create containers, change clusters, or print secrets. They help development by showing whether the local AI engineering bench is ready for remote execution work.
Security rule. Do not put provider tokens, remote credentials, or private keys into package policy, target policy, guide examples, or postcheck logs. A future Runpod-specific step should be added only when it can externalize secrets and explain dry-run behaviour clearly.

12. Scenario: OpenClaw, local models, and personal knowledge work

Scenario. You want a local model to help reason about your personal knowledge base, biological theory, mathematical assumptions, infrastructure notes, and paper structure. You also want to avoid hard-coding private vault paths into public config or documentation.

Use the AI engineer role to prepare OpenClaw and local model tooling. Use the publisher role when the result becomes writing, synthesis, and draft production. Keep the vault path private and policy-driven. The tool can check that a configured workspace exists, but it should not run an agent or assume a private path unless you explicitly configure it. 

# Prepare OpenClaw and local model checks from the operator seat.
sudo config --target aiengineer bootstrap step check_openclaw_base_requirements
sudo config --target aiengineer bootstrap step install_openclaw_full_stack
sudo config --target aiengineer bootstrap step check_openclaw_agent_workspace

# Work inside the AI engineer identity for model/service development.
su - aiengineer
lv conda aiengineer
cd ~/projects/openclaw-local
Installer groundwork. The OpenClaw steps are registered managed steps. The install step reads the OpenClaw package stack; the check steps should remain non-mutating. They help development by preparing local model and workspace capability without running a private agent or exposing personal knowledge base contents.

A useful local model workflow is to ask narrow questions: explain the biological role of an interaction, compare a mathematical model assumption, outline a parameter-search strategy, or identify what belongs in the methods section. The tool should prepare the bench; your research process decides what evidence is trusted.

13. Scenario: paper writing, Obsidian, and LaTeX draft production

Scenario. The model work is mature enough to write. You want the publisher role to reach the writing workspace or Obsidian vault, convert notebooks, use a prepared LaTeX template, and produce a final draft without mixing manuscript work into research or engineering accounts.

Prepare the publisher role

config --target publisher config-show
sudo config --target publisher credentials per-share
sudo config --target publisher mount
sudo config --target publisher bootstrap step install_publisher_base_tools
sudo config --target publisher bootstrap step install_publisher_notebook_stack
sudo config --target publisher bootstrap step install_pandoc_obsidian_tools
Installer groundwork. The publisher install steps read publisher package stacks from package policy and call trusted functions through the managed step path. The Pandoc/Obsidian step should be a safe check or preparation step; it must not assume private vault paths in public defaults. This helps publishing by making notebook export and document conversion repeatable.

Write as the publisher

su - publisher
lv conda publisher
cd ~/writing/grn-paper

# Convert analysis output into draft material.
conda run -n publisher jupyter nbconvert --to markdown ../analysis/results.ipynb

# Use an already prepared LaTeX template.
pandoc manuscript.md --template template.tex -o draft.tex
latexmk -pdf draft.tex
How this helps publishing. The publisher role becomes the writing bench. It can see the publishing workspace according to mount policy, use export tools in its own environment, and produce a LaTeX draft without becoming the research scientist or AI engineer. That separation keeps the paper pipeline clean and auditable.

Use OpenClaw for structure, not unchecked truth

A local model can help turn your personal knowledge base into a structured outline, identify missing methods details, compare biological interpretations, or suggest how to explain mathematical theory. It should not silently rewrite evidence. Keep the model's output as a drafting assistant, then verify claims against notebooks, equations, figures, and source material.

14. Scenario: data boundaries, mounts, and credentials

The config tool treats shares as workflow boundaries. Ingress is material entering the workflow. Egress is material leaving it. Research is sensitive scientific work. Publish is the writing/export boundary. Distrohome and scripting support configuration and tool synchronisation. The local target user and the remote SMB user are related, but they are not the same thing. 

config --target researchscientist config-show
sudo config --target researchscientist credentials per-share
sudo config --target researchscientist mount

config --target publisher config-show
sudo config --target publisher credentials per-share
sudo config --target publisher mount
How this helps research and publishing. The research scientist can receive research-oriented access without giving the publisher unnecessary research write access. The publisher can reach publishing material without becoming the research identity. Credential files stay private to the relevant target.

16. Troubleshooting by symptom

A package is missing

Use lv to confirm which environment you are inspecting. If the package was useful only once, keep it in the prototype env. If it belongs to a repeatable role, add it to the correct package stack and run the managed step again.

A step exists but does not run

Check bootstrap status. The step may be skipped in the target plan or blocked by a marker. That is not failure; it is the tool protecting you from accidental reruns.

Files have the wrong owner

Ask whether you were preparing with config --target or working with su - USER. Real research and writing files should be created by the target role, not casually by the operator.

Remote or private data appears in logs

Stop and remove the output. The tool should print paths, state, and redacted identity information, not passwords, vault contents, datasets, or private notes.
