Config Tool Workflows

A technical workflow article for using the vmuser config tool to provision role accounts, separate operator and target concerns, manage Python environments, run AI platform and research experiments, and extend the system safely with managed install steps.

Abstract. The config tool is a controlled orchestration layer for WSL/Linux role environments. Instead of manually installing tools into whichever shell happens to be active, it separates account identity, profile policy, Python environment selection, bootstrap plans, and trusted installer functions. This makes it possible to run an AI engineering platform, scientific research workflows, publisher tooling, and temporary experiments side by side without contaminating each other. The article below explains the operating model, then walks through concrete scenarios: creating accounts, validating profile kind, applying password policy, choosing Python environments, running one managed step, comparing the managed flow to manual installs, and adding new workflow functions.

1. System model

Scenario. You are logged in as the operator account, usually vmuser, but you are configuring another account such as aiengineer, researchscientist, or publisher. The main risk is confusing the account running the command with the account being configured. The model below keeps that boundary explicit.
Key insight. The tool is not just an installer. It is a policy-to-execution pipeline. Account profiles describe who the target is, target env files describe what policy applies, bootstrap plans decide what may run, and trusted functions perform the work.

Workflow boundary. Config files are policy. Shell functions are execution. Runtime markers are history. Do not store passwords, secrets, raw datasets, manuscript content, or arbitrary shell code in policy files.

2. Account lifecycle scenario

Scenario. You need a new AI engineer, research scientist, or publisher account. You want the user, group, home permissions, SMB profile, mount profile, bootstrap profile, and target env file created consistently from one profile instead of manually building each piece.
Key insight. Account creation should produce an inspectable target policy before anything else. Dry-run first, then apply. Password setup is deliberately interactive unless explicitly handled through Linux tools such as passwd and chage.

Target account flow

sudo config --create-target --profile AIEngineer --name aiengineer --dry-run
sudo config --create-target --profile AIEngineer --name aiengineer --interactive

sudo config --create-target --profile ResearchScientist --name researchscientist --dry-run
sudo config --create-target --profile Publisher --name publisher --dry-run

Operator account flow

sudo config --create-operator --profile DefaultOperator --name vmuser --dry-run
sudo config --create-operator --profile DefaultOperator --name vmuser --interactive
Command intent. --create-target is for accounts that receive role-specific policy. --create-operator is for accounts that own or operate the tool. The selected profile kind must match the command kind.

Password and first-login expiry

# interactive create can ask whether to run passwd USER
sudo config --create-target --profile AIEngineer --name aiengineer --interactive

# expire at first login, after a password exists or was just set
sudo config --create-target --profile AIEngineer --name aiengineer --interactive --expire-password

# manual fallback
sudo passwd aiengineer
sudo chage -d 0 aiengineer
Expected behavior. Interactive mode can prompt to set a password. Non-interactive mode must not prompt and should print the later sudo passwd USER command. --expire-password should not run blindly if no password was set.

Removal workflow once the lifecycle tasks are implemented

sudo config --remove-target --name aiengineer --dry-run
sudo config --remove-target --name aiengineer --keep-home
sudo config --remove-target --name aiengineer --remove-home
sudo config --remove-target --name aiengineer --purge-config

sudo config --remove-operator --name oldoperator --dry-run
Removal rule. The safe default keeps home directories, state, target env files, and credentials. Destructive removal must be explicit.

3. Profile-kind validation scenario

Scenario. You accidentally run --create-operator with --profile AIEngineer. Without validation, the tool can produce a target policy from an operator command, which is misleading and dangerous.
Key insight. The command type is part of the contract. Operator commands must accept only operator profiles. Target commands must accept only target profiles. When there is a mismatch, the tool should fail and suggest valid profiles from accounts/profiles.tsv.
CommandValid profile kindValid examplesShould reject
create-operatoroperatorDefaultOperatorAIEngineer, ResearchScientist, Publisher, DefaultTarget
create-targettargetDefaultTarget, AIEngineer, ResearchScientist, PublisherDefaultOperator

Mismatch: operator command with target profile

config --create-operator --profile AIEngineer --name testengineer --dry-run --expire-password

Expected error shape:

[ERROR] Profile kind mismatch.
[ERROR] Command kind: operator
[ERROR] Profile AIEngineer has account_kind=target
[INFO] Use create-target for target profiles, or choose one of these operator profiles:
  - DefaultOperator

Mismatch: target command with operator profile

config --create-target --profile DefaultOperator --name testoperator --dry-run

Expected error shape:

[ERROR] Profile kind mismatch.
[ERROR] Command kind: target
[ERROR] Profile DefaultOperator has account_kind=operator
[INFO] Use create-operator for operator profiles, or choose one of these target profiles:
  - DefaultTarget
  - AIEngineer
  - ResearchScientist
  - Publisher
Implementation note. Do not hard-code the suggestions if possible. Read the valid profiles from accounts/profiles.tsv by filtering the second column, account_kind.

4. Role setup scenario map

Scenario. You want to configure multiple working identities on the same machine: an operator, a generic target, an AI engineer, a research scientist, and a publisher. Each identity needs different SMB access, mounts, bootstrap defaults, and Python environment policy.
Key insight. A role is not only a Linux user. In this system, a role is the combination of account profile, target env, SMB profile, mount profile, bootstrap profile, and later Python env profile.

5. Python environment policy scenario

Scenario. You need one stable AI engineering environment, one stable research environment, one publishing environment, and temporary experiment environments. You do not want packages installed into base by accident, and you do not want the active shell environment to control managed installs silently.
Key insight. Functions are global; Python packages are environment-specific. The same managed step can be reused across roles, but it must print and use the resolved PYTHON_ENV.
Account profileAIEngineer
Target roleai-engineer
Python env profileaiengineer
Target envPYTHON_ENV=aiengineer
Installerpip install into aiengineer

Source of truth

AIEngineer          ai-engineer          aiengineer          auto         0               0             AI platform and ML tooling
ResearchScientist   research-scientist   researchscientist   auto         0               0             Research and simulation tooling
Publisher           publisher            publisher           auto         0               0             Publishing and notebook tooling

Target env result

PYTHON_ENV="aiengineer"
PYTHON_ENV_MANAGER="auto"
PYTHON_ENV_CREATE_MISSING="0"
PYTHON_ENV_ALLOW_SYSTEM="0"

Override to an experiment env

# in targets/aiengineer.env
PYTHON_ENV="experiment1"

sudo config --target aiengineer bootstrap step install_pytorch_stack
Do not silently use the currently active shell env. Do not install into system Python unless explicitly allowed. Do not use sudo pip.

6. AI platform development scenario

Scenario. You are building an AI-powered platform: API services, LLM tooling, model development utilities, MLOps scripts, and possibly Kubernetes or Runpod workflows. This should live in the stable aiengineer role environment, not in throwaway experiment envs.
Key insight. The AI platform environment should be boring and reproducible. Experimental package pins should be tested elsewhere before being promoted into the stable role env. 
# create/reconcile account
sudo config --create-target --profile AIEngineer --name aiengineer --dry-run
sudo config --create-target --profile AIEngineer --name aiengineer --interactive --expire-password

# inspect target policy
config --target aiengineer config-show

# create env manually if policy says create_missing=0
sudo -H -u aiengineer bash -lc 'conda create -n aiengineer python=3.11'

# install stable platform stacks one step at a time
sudo config --target aiengineer bootstrap step install_ml_base_python_stack
sudo config --target aiengineer bootstrap step install_llm_stack
sudo config --target aiengineer bootstrap step install_api_stack
sudo config --target aiengineer bootstrap step install_ml_dev_tools

# run platform code inside the env
sudo -H -u aiengineer bash -lc 'conda run -n aiengineer python -m uvicorn app:app --reload'

7. Parallel experiment scenario

Scenario. You want to test a new Torch build, a new Transformers version, or a model stack without risking the stable AI platform environment. You create a named experiment env and run the same managed step into that env explicitly.
Key insight. Experiment environments are allowed to be unstable. Stable role environments should not be. The difference is enforced by explicit PYTHON_ENV selection. 
# create isolated experiment env
sudo -H -u aiengineer bash -lc 'conda create -n torch-nightly python=3.11'

# override target/session policy
sudoedit /home/vmuser/.local/etc/config-sh/targets/aiengineer.env
# set: PYTHON_ENV="torch-nightly"

# run only relevant steps
sudo config --target aiengineer bootstrap step install_pytorch_stack
sudo config --target aiengineer bootstrap step check_pytorch_cuda

# verify
sudo -H -u aiengineer bash -lc 'conda run -n torch-nightly python -c "import torch; print(torch.__version__, torch.cuda.is_available())"'
After an experiment, either keep the env for reproducibility, delete it, or promote its package versions into role defaults if it becomes the new standard.

8. Research workflow scenario

Scenario. You are running scientific exploration, simulation, parameter search, or GRN/Turing-pattern research. You need reliable scientific Python tooling, but you also want per-project environments for specific hypotheses or papers.
Key insight. Research tooling should be reproducible and separate from platform engineering. Project-specific environments prevent one paper or experiment from destabilizing the general research role. 
# create/reconcile role
sudo config --create-target --profile ResearchScientist --name researchscientist --dry-run

# stable research tooling
config --target researchscientist config-show
sudo config --target researchscientist bootstrap step install_grn_research_python_stack
sudo config --target researchscientist bootstrap step install_parameter_search_tooling

# project-specific env
sudo -H -u researchscientist bash -lc 'conda create -n grn-exp-a python=3.11'
sudoedit /home/vmuser/.local/etc/config-sh/targets/researchscientist.env
# set: PYTHON_ENV="grn-exp-a"

sudo config --target researchscientist bootstrap step install_grn_research_python_stack
Keep raw research data, unpublished datasets, and manuscript text out of config files and postcheck logs. Env policy references tooling, not private content.

9. Publisher workflow scenario

Scenario. You are preparing notebooks, manuscript exports, Pandoc/LaTeX workflows, or publishing utilities. This role should have document tooling and reproducible export tools without inheriting the heavier AI platform stack.
Key insight. Publishing is a separate operational role. Keep it light, explicit, and focused on transformation/export tooling rather than model experimentation. 
sudo config --create-target --profile Publisher --name publisher --dry-run
config --target publisher config-show

sudo config --target publisher bootstrap step install_publisher_base_tools
sudo config --target publisher bootstrap step install_pandoc_obsidian_tools

sudo -H -u publisher bash -lc 'conda run -n publisher python -m pip list'

10. Managed workflow versus manual installs

Scenario. You could manually run pip install, apt install, or conda install in each account. That works once, but it does not scale when you need consistent setup across roles, repeatable experiments, and clear recovery after failures.
Key insight. Manual installs optimize for speed now. Managed installs optimize for repeatability, isolation, and knowing what changed.
Daily problemManual install habitManaged workflow
Wrong envActivate an env manually and hope it is right.PYTHON_ENV is resolved from target/profile and printed before install.
ReproducibilityCommands live in shell history or notes.Package sets live in config defaults and trusted functions.
Parallel experimentsNew pins can contaminate base.Override to experiment1 for one target/step.
Role setupRemember separate commands for each role.Profiles choose mount/SMB/bootstrap/env defaults.
Audit trailNo consistent record of what ran.Plan and markers record pending/done/skipped/failed.
Safetysudo pip or system Python mistakes.System Python blocked unless explicitly allowed.

12. Command recipes with intent

Scenario. You are at the shell and need to know the shortest safe command for the job. Each command below is grouped by intent so you can avoid broad execution when inspection or one-step execution is enough.

Inspect profile and target policy

Intent. See what the tool believes a role is before running anything.
config profiles
config --target aiengineer config-show
config --target researchscientist config-show
config --target publisher config-show

Bootstrap plan and one-step run

Intent. Run one selected step through the same safety gates as full bootstrap, without running the full plan.
config --target aiengineer bootstrap steps
sudo config --target aiengineer bootstrap status
sudo config --target aiengineer unskip install_ml_base_python_stack
sudo config --target aiengineer bootstrap step install_ml_base_python_stack

Check envs

Intent. Confirm which Python environments exist for each target user.
sudo -H -u aiengineer bash -lc 'conda env list'
sudo -H -u researchscientist bash -lc 'conda env list'
sudo -H -u publisher bash -lc 'conda env list'

Check imports inside exact env

Intent. Verify that packages landed in the intended env, not in base or system Python.
sudo -H -u aiengineer bash -lc 'conda run -n aiengineer python -c "import fastapi, transformers; print(\"ok\")"'
sudo -H -u researchscientist bash -lc 'conda run -n researchscientist python -c "import numpy, scipy; print(\"ok\")"'
sudo -H -u publisher bash -lc 'conda run -n publisher python -c "import nbconvert; print(\"ok\")"'

Credentials and mounts

Intent. Create per-share credential files and mount only the shares allowed by the target policy.
sudo config --target aiengineer credentials per-share
sudo config --target aiengineer mount

sudo config --target publisher credentials per-share
sudo config --target publisher mount
