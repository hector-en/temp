Config Tool Developer Guide

A contributor-focused technical article for developers extending the vmuser configuration tool: architecture, design rules, code paths, profile modeling, managed installers, safe dispatch, state semantics, testing, and contribution checklists.

Abstract. The config tool is a shell-based orchestration system for provisioning role-specific Linux/WSL accounts and their development environments. It deliberately separates editable policy from executable behavior. Developers contributing to it should understand the difference between account profiles, target env policy, bootstrap plans, runtime markers, and trusted installer functions before changing code. This guide explains the internal model and shows how to add new capabilities without weakening the safety boundary: add a trusted function, allowlist it, register it, place it in role plans, test it with one target and one step, then document the behavior.

1. Who this guide is for

Scenario. You want to contribute a new role, installer, account lifecycle command, Python environment rule, SMB/mount behavior, or bootstrap plan feature. You need to know which file to edit and how to avoid breaking target isolation.

This guide is for developers who will modify the implementation, not only operate the tool. It assumes you are comfortable reading shell scripts and that you will validate changes with syntax checks and dry-runs before applying them.

Main rule. When adding behavior, ask: is this policy, execution, state, or documentation? Each belongs in a different place.
Change typeWhere it belongsExample
Stable policyetc/config-sh/**/*.env or accounts/*.tsvDefault SMB user, mount profile, Python env name.
Executable behaviorlib/config-sh/installers.sh or trusted functions in config.shInstall packages, create account, reconcile files.
Step metadatabootstrap/steps.tsvStep name, function name, scope, network flag.
Runtime state/home/USER/.local/state/config-shbootstrap.plan, *.done, *.skipped.
Developer docsHTML guides, milestone specs, run instructionsHow to use, test, and extend a feature.

3. Safety model and contribution contract

Scenario. A contributor wants to make the tool more flexible by letting steps.tsv call any function by name. That is convenient, but it breaks the core trust boundary.
Do not let editable files execute arbitrary code. Files such as .env, .tsv, and .plan are operator-editable policy. They must describe intent, not execute shell.

Contribution contract

  • Executable behavior goes into trusted shell functions.
  • Trusted functions must be allowlisted before a manifest can dispatch them.
  • Target-aware behavior must use TARGET_USER and TARGET_HOME, not hard-coded usernames.
  • System-level changes must require sudo and be explicit in step scope.
  • Python installs must target explicit env policy and avoid accidental system Python.
  • Credentials must never be printed, copied into logs, or inspected casually.
  • Dry-run must show enough detail to catch wrong account/profile/scope decisions.

Safe default hierarchy

AreaSafe defaultExplicit override
Account creationDry-run before apply.--interactive or --non-interactive.
Password handlingDo not accept passwords on command line.Run passwd USER interactively.
Account removalKeep home, config, state, credentials.--remove-home, --purge-config.
Python packagesDo not install into system Python.PYTHON_ENV_ALLOW_SYSTEM=1.
Bootstrap executionRun one step for validation.Full bootstrap only after plan is trusted.

5. CLI switches and command design

Scenario. You need to add a new command option. Before adding it, decide whether it is stable policy, one-time runtime choice, or a dangerous/destructive operation.
Design rule. Stable role defaults belong in config files. One-time operator decisions belong in switches. Destructive actions should require explicit switches and clear dry-run output.
SwitchMeaningRationaleDeveloper note
--target USERChoose affected account.Operator may configure many targets.Do not infer target from current shell when command is target-sensitive.
--profile NAMEChoose account profile.Creation-time role choice.Validate profile kind against command kind.
--dry-runShow plan without mutation.Current system state matters.Dry-run should expose owner/mode, home, groups, target env, password policy.
--interactivePrompt before applying.Safe for manual operator sessions.May prompt for choices, but do not expose passwords.
--non-interactiveNo prompts.Needed for scripted/Codex runs.Must never block waiting for input.
--expire-passwordForce first-login password change.One-time account lifecycle action.Only run after password exists or was set.
--remove-homeDelete target home.Destructive, explicit only.Warn that state/credentials under home are removed too.
--purge-configRemove target env policy.Destructive policy cleanup.Default should keep policy for audit/recovery.

Bad switch design

# Bad: silently destructive default
sudo config --remove-target --name aiengineer

# Bad: password value on command line
sudo config --create-target --name aiengineer --password "secret"

Good switch design

# Good: inspect first
sudo config --remove-target --name aiengineer --dry-run

# Good: explicit destructive behavior
sudo config --remove-target --name aiengineer --remove-home --purge-config

6. Profile system: accounts, SMB, mounts, Python envs

Scenario. You want to add a new role, such as DataEngineer or BioModeler. That role needs a Linux user, a role group, SMB identities, mount choices, bootstrap defaults, and probably Python env policy.
Design rule. Profiles model role policy. They should be readable, auditable, and mostly static. Runtime execution should not be hidden inside profiles.

Profile files

FilePurposeTypical edit
accounts/profiles.tsvAccount kind, username, groups, role labels, bootstrap profile, SMB profile, mount profile.Add or modify role definitions.
accounts/smb-profiles.tsvSMB usernames per share type.Change share identities for a role.
accounts/mount-profiles.tsvEnabled share groups.Control which mounts a role receives.
install/python-env-profiles.tsvPython env name and manager policy by role.Assign envs such as aiengineer, researchscientist, publisher.

Account kind matters

The second column in profiles.tsv, account_kind, is not decoration. It decides whether a profile is valid for create-operator or create-target. 

# valid operator profile
DefaultOperator    operator    vmuser    operator    operator    770    operator    Operator    operator    operator    all    1    1    1    Operator account

# valid target profile
AIEngineer         target      aiengineer    aiengineer    aiengineer    770    ai-engineer    AI Engineer    ai-engineer    aiengineer    research    0    1    1    AI engineering role
Contributor note. When adding a profile, immediately test both the valid and invalid command path. Example: 
sudo config --create-target --profile AIEngineer --name aiengineer --dry-run
config --create-operator --profile AIEngineer --name badoperator --dry-run

7. Bootstrap plan and state semantics

Scenario. A new step is added and appears in steps.tsv, but the target does not run it. The reason is usually plan/marker state, not missing code.
Design rule. The bootstrap plan says what may run. Markers say what already happened. The engine reconciles those two views before execution.
StateMeaningDeveloper implication
pending STEPPlan allows this step to run.Execution still checks markers.
next STEPOperator intent marker; treated like pending.Useful for human planning.
skipped STEPPlan blocks this step.Do not run even if function exists.
STEP.doneStep completed before.run_once skips it.
STEP.skippedMarker blocks the step.unskip removes it.
STEP.failedStep failed before.Status should show reason if available.
STEP.runningStep is running or was interrupted.Lock/stale state needs careful handling.

Contribution note

Avoid changing run_once unless you are explicitly working on state semantics. Most new features should enter as new steps, not by changing the runner. 

sudo config --target aiengineer bootstrap status
sudo config --target aiengineer unskip install_example_tooling
sudo config --target aiengineer bootstrap step install_example_tooling

8. Managed installers and step dispatch

Scenario. You want to add InstallMLBasePythonStack. If you only add the function, operators cannot safely discover or run it. If you only add a row to steps.tsv, the engine should reject it unless it is allowlisted.
Design rule. A managed installer is complete only when it has implementation, trust, metadata, role placement, and a one-step validation path.

The complete chain

Implementationinstallers.sh
InstallExampleTooling
Trustconfig.sh
config_bootstrap_function_allowed
Metadatasteps.tsv
install_example_tooling
Role defaultprofiles/*.plan
pending/skipped
Validationbootstrap step
one target, one step

Installer function expectations

  • Print what target and environment it is affecting.
  • Return non-zero only for real failures.
  • Skip clearly when optional config is missing.
  • Use target-aware helpers for target-owned files.
  • Do not assume $HOME means TARGET_HOME.
  • Do not print secrets or credential file contents.
  • Prefer idempotent operations.
InstallExampleTooling() {
  local target_user="${TARGET_USER:-}"
  local target_home="${TARGET_HOME:-}"

  if [[ -z "$target_user" || -z "$target_home" ]]; then
    echo "[ERROR] TARGET_USER/TARGET_HOME not set" >&2
    return 1
  fi

  echo "[INFO] Installing example tooling for ${target_user}"
  install -d -m 755 -o "$target_user" -g "$(id -gn "$target_user")" "${target_home}/.local/bin"

  # real work here
}

9. How to add a new managed function

Scenario. A manual workflow has become repeatable: install a Python package set, configure a CLI, add notebooks, install publisher tooling, or check GPU/Torch support. It should become a managed step.

Step 1: name the step and function

ThingConventionExample
Step namelowercase snake caseinstall_ml_base_python_stack
Function namePascalCase shell functionInstallMLBasePythonStack
Package variableuppercase env-style namePIP_ML_BASE_STACK

Step 2: implement trusted function

# /home/vmuser/.local/lib/config-sh/installers.sh
InstallMLBasePythonStack() {
  local packages="${PIP_ML_BASE_STACK:-}"
  [[ -n "$packages" ]] || {
    echo "[SKIP] PIP_ML_BASE_STACK is empty"
    return 0
  }

  echo "[INFO] Installing ML base Python stack for ${TARGET_USER}"
  InstallPythonPackagesIntoEnv "${PYTHON_ENV:-}" $packages
}

Step 3: add allowlist entry

# /home/vmuser/.local/bin/config.sh
config_bootstrap_function_allowed() {
  case "$1" in
    ...|InstallMLBasePythonStack)
      return 0
      ;;
    *)
      return 1
      ;;
  esac
}

Step 4: register in steps.tsv

install_ml_base_python_stack    InstallMLBasePythonStack    target    1    Install base ML Python packages into the target env

Step 5: add to profile plans

# ai-engineer.plan
pending install_ml_base_python_stack

# research-scientist.plan
skipped install_ml_base_python_stack

# publisher.plan
skipped install_ml_base_python_stack

Step 6: validate one step

bash --noprofile --norc -n /home/vmuser/.local/bin/config.sh
bash --noprofile --norc -n /home/vmuser/.local/lib/config-sh/installers.sh

config --target aiengineer bootstrap steps
sudo config --target aiengineer bootstrap status
sudo config --target aiengineer unskip install_ml_base_python_stack
sudo config --target aiengineer bootstrap step install_ml_base_python_stack

10. How to add a new profile or role

Scenario. You need a new role such as DataEngineer. It should get its own user defaults, role group, SMB identity, mount profile, bootstrap profile, and Python environment.

Checklist

  1. Add account profile row in accounts/profiles.tsv.
  2. Add SMB profile row in accounts/smb-profiles.tsv if needed.
  3. Add mount profile row in accounts/mount-profiles.tsv if needed.
  4. Add bootstrap profile file under bootstrap/profiles/.
  5. Add Python env profile row in install/python-env-profiles.tsv if AN2-02 is implemented.
  6. Ensure config-init can generate the example row/file for new installs.
  7. Dry-run create-target with valid and invalid profile-kind paths.
sudo config --create-target --profile DataEngineer --name dataengineer --dry-run
config --create-operator --profile DataEngineer --name badoperator --dry-run
Important. Adding a profile is not enough to install tools. Profiles choose defaults. Installers do execution later through bootstrap steps.

11. How to add environment-aware Python installers

Scenario. A contributor adds a Python package installer. It works on their shell because the right conda env is active, but it fails for targets or installs into the wrong environment during automation.
Design rule. Managed Python installers must not depend on the active shell. They must resolve an explicit target environment.

Resolution order

ResolveTargetPythonEnv:
  1. explicit env argument
  2. PYTHON_ENV from targets/USER.env
  3. CONFIG_PYTHON_ENV_DEFAULT if defined
  4. refuse system Python unless PYTHON_ENV_ALLOW_SYSTEM=1
  5. if env missing and PYTHON_ENV_CREATE_MISSING=0, fail or skip clearly

What to print

target user: aiengineer
target role: ai-engineer
target Python env: aiengineer
env manager: auto
installing packages from PIP_ML_BASE_STACK into aiengineer

Why this matters

A virtualenv or conda env named experiment1 does not automatically see packages installed into base or aiengineer. That isolation is useful only if the installer prints and uses the intended environment.

Do not use sudo pip. Do not install into system Python silently. Do not assume conda activate happened in the calling shell.

12. Account lifecycle extension notes

Scenario. A developer adds --expire-password, remove-target, or remove-operator. These are lifecycle features, not installer steps, so they belong in the account command path.

Where lifecycle behavior belongs

FeatureLikely code pathImportant rule
--expire-passwordconfig_run_create_account, config_apply_account_planOnly expire after password exists or was set.
profile-kind validationAfter config_resolve_account_profileFail before printing/applying mismatched plan.
remove-targetNew remove account helper path in config.shConservative default: keep home/config/state/credentials.
remove-operatorSeparate guarded operator removal pathRefuse current operator; protect vmuser unless forced.

Profile-kind validation placement

config_resolve_account_profile "$resolved_profile" ...
config_validate_account_plan_kind "$kind" || return 1
config_print_account_plan_summary
config_print_account_plan_actions
Why placement matters. Before profile resolution, the code does not know the profile kind. After the apply path, the wrong policy may already be written.

13. Testing and validation

Scenario. You have made a change and need to prove it did not break parsing, profile resolution, dry-run safety, target ownership, or step dispatch.

Always run syntax checks

bash --noprofile --norc -n /home/vmuser/.local/bin/config.sh
bash --noprofile --norc -n /home/vmuser/.local/lib/config-sh/installers.sh
bash --noprofile --norc -n /home/vmuser/.local/bin/mounts.sh
bash --noprofile --norc -n /home/vmuser/.local/bin/create-cifs-credentials-files.sh

Dry-run account tests

sudo config --create-operator --profile DefaultOperator --name vmuser --dry-run
sudo config --create-target --profile AIEngineer --name aiengineer --dry-run
sudo config --create-target --profile ResearchScientist --name researchscientist --dry-run
sudo config --create-target --profile Publisher --name publisher --dry-run

Negative tests

config --create-operator --profile AIEngineer --name badoperator --dry-run
config --create-target --profile DefaultOperator --name badtarget --dry-run

Step visibility tests

config --target aiengineer bootstrap steps
sudo config --target aiengineer bootstrap status

One-step execution test

sudo config --target aiengineer unskip install_example_tooling
sudo config --target aiengineer bootstrap step install_example_tooling
sudo config --target aiengineer bootstrap status
For destructive commands, start with --dry-run. If the feature removes users, homes, config files, or state, include explicit negative tests proving safe refusals.

14. Review checklist

Before merging a contribution, verify:
  • The change has a clear scope: account lifecycle, profile policy, bootstrap, installer, mount, credential, or docs.
  • Executable behavior is not hidden in editable config files.
  • New installer functions are allowlisted and registered in steps.tsv.
  • New steps are placed in appropriate role profile plans as pending or skipped.
  • Target-specific file writes use TARGET_USER and TARGET_HOME.
  • Operator-owned policy files remain operator-owned and mode 600 where appropriate.
  • Credential files are not read or printed.
  • Dry-run output exposes the important owner/group/mode/scope decisions.
  • Syntax checks pass.
  • Negative tests are included for dangerous or mismatched command paths.
  • The final answer or changelog lists changed files and tests run.

Commit message patterns

feat: add managed ML base workflow step
feat: add profile-aligned Python env policy
fix: reject account profile kind mismatches
fix: preserve operator ownership for target env files
docs: add developer contribution guide
chore: register publisher workflow profile steps

15. Anti-patterns

Anti-patternWhy it is badBetter approach
Put shell commands in .env files.Turns policy into execution.Put commands in trusted functions.
Let steps.tsv call arbitrary functions.Breaks the allowlist trust boundary.Require config_bootstrap_function_allowed.
Use $HOME in target installers.May point to root/operator, not target.Use TARGET_HOME and target helpers.
Use sudo pip.Can damage system Python and mix envs.Resolve PYTHON_ENV and install inside it.
Default to deleting homes/config during removal.Destructive and hard to recover.Default keep; require explicit destructive switches.
Run full bootstrap to test one new step.Can run unrelated installers.Use bootstrap step STEP.
