Config Tool Workflows

A holistic technical article for understanding and extending the vmuser configuration system: role accounts, target isolation, SMB security, ingress/egress/research/publish shares, encrypted sensitive storage, pull/push drift control, Python environments, managed installers, and safe developer contribution patterns.

Abstract. The config tool is a controlled orchestration layer for WSL/Linux role environments. It separates account identity, profile policy, SMB access policy, mount policy, Python environment selection, bootstrap plans, runtime state, and trusted installer functions. That separation matters because this system is not only installing packages: it also protects target identities from external systems, routes ingress and egress shares through explicit policies, lets the operator pull configuration from distrohome to avoid local drift, pushes per-user backups when appropriate, and keeps sensitive shares such as research/publish data behind account-specific SMB credentials and encryption. The article below explains the operating model, then walks through concrete scenarios: creating accounts, validating profile kind, applying password policy, choosing Python environments, running one managed step, comparing managed workflows to manual installs, extending the tool, and reasoning about the security boundaries that connect SMB, mounts, encryption, and per-target configuration.

SMB and mount boundaries

SMB is the external trust boundary. The local Linux target account is not automatically the same as the SMB account. That is why the system keeps SMB identity in profile policy and writes separate credential files under the target user's private data directory.

Share or credentialPurposeTypical access meaningDeveloper caution
distrohome.credentialsRemote distro/home configuration source.Used to pull known config files back into the local WSL layout.Do not mix this with research data. It is about configuration drift control.
scripting.credentialsRemote scripting/tooling source.Used for shared scripts or operator-managed tool material.Keep executable trust separate from arbitrary remote files.
ingress.credentialsInbound data/work queue.Material entering the local workflow.Treat as untrusted input unless validated.
egress.credentialsOutbound/export/share area.Material leaving the local workflow.Do not push private research or secrets accidentally.
research.credentialsSensitive research share.Research-only datasets, notebooks, models, or protected material.Should be available only to roles that explicitly need research access.
publish.credentialsPublishing/export share.Publisher or publication pipeline outputs.Keep manuscript/vault source separate from public exports.
What the credential creation code does. The credential helper does not mount anything by itself. It creates per-share credential files, usually under /home/USER/.local/share/wsl-mounts, with target-owned permissions. Later, mounts.sh uses those files to mount only the shares enabled by the target's mount policy. 
sudo config --target aiengineer credentials per-share
sudo config --target aiengineer mount
What this code does. The first command creates or refreshes target-owned SMB credential files for the selected target. The second command uses the target's mount profile to mount the allowed shares. For an AI engineer with the research mount profile, this usually means ingress, egress, and research are available, while publish or distrohome may remain disabled unless policy allows them.

Ingress, egress, research, publish, and distrohome

The share names encode workflow intent. ingress is for inbound work or data. egress is for outbound results. research is for sensitive research material. publish is for publication-oriented material. distrohome is not just another data share: it supports configuration synchronization so local environments do not drift silently.

Encryption and sensitive-file access

The SMB layer controls remote authentication. File encryption adds another boundary after data is present. The intended model is that sensitive files, such as research material, remain protected so that only the account or identity with the right key or SMB login context can read them. In practice, this means developers should treat encrypted research/publish areas as role-specific and should not add helper functions that copy, print, or re-permission them broadly.

Developer caution. Never add a debugging helper that prints credential file contents, dumps mounted research folders, copies encrypted material into logs, or changes permissions broadly. If a function needs to prove access, print paths, ownership, mount status, and redacted identity—not file contents or secrets.

Why target isolation matters

Target isolation prevents three kinds of drift: identity drift, configuration drift, and data-boundary drift. Identity drift happens when a command meant for aiengineer runs as vmuser or root. Configuration drift happens when local settings diverge from distrohome without an intentional pull/push. Data-boundary drift happens when research, publish, ingress, and egress are treated as generic folders instead of separate security and workflow zones.

Contributor rule. When changing mount, credential, pull, or push behavior, always answer four questions in the code or documentation: Which local user is affected? Which SMB identity is used? Which share is involved? Which data boundary is crossed?

2. Code rationale: why the tool is structured this way

Scenario. You are reading or modifying the code and need to understand why the tool separates profiles, switches, target env files, installers, step registries, and state markers instead of simply running shell commands directly.
Key insight. The code is built around one safety principle: user-editable files may describe intent, but only trusted shell functions may execute work. That is why new functionality normally requires a function, an allowlist entry, a step registry row, and profile/plan placement.
Code areaWhat it doesWhy it existsWhen you edit it
config_parse_global_args Reads global switches such as --target, then decides which command is being run. Separates “who this affects” from “what command to run.” Only when adding global CLI behavior that applies to every command.
config_set_target_user Resolves TARGET_USER, TARGET_HOME, loads config files, and refreshes session context. Prevents commands from accidentally using the operator home when they are meant for a target. Only when target context rules change.
config_run_create_account Parses account creation switches, resolves the selected profile, supports dry-run/interactive/non-interactive modes. Turns account creation into an inspectable plan before changing the system. When adding account lifecycle switches such as --expire-password.
config_resolve_account_profile Reads profiles.tsv, smb-profiles.tsv, and mount-profiles.tsv, then builds the account plan variables. Centralizes role policy so it is not scattered through shell logic. When the profile model gains new columns or derived values.
config_reconcile_target_env_file Writes the managed block in targets/USER.env and restores owner/group/mode. Keeps generated policy consistent and avoids root-owned target env regressions after sudo operations. When generated target policy gains new variables.
config_bootstrap_function_allowed Lists trusted function names that may be dispatched from step metadata. Prevents editable TSV files from calling arbitrary shell functions. Every time you add a new managed install/check function.
config_bootstrap_step_rows Reads steps.tsv or falls back to built-in step rows. Makes steps declarative while preserving a safe fallback if metadata is broken. Normally edit steps.tsv, not this function, unless registry behavior changes.
run_once Runs one step if not done/skipped, writes running/done/failed markers, handles locks and logs. Gives each step idempotent state, failure visibility, and protection from accidental reruns. Only when changing state semantics.
installers.sh Contains actual install/check functions. Keeps execution in trusted source instead of user-editable config. Every time you add a real capability.

Why profiles exist

Profiles are reusable policy templates. They keep role decisions outside shell logic and make dry-run output predictable. A profile says: “for this kind of user, choose these groups, SMB identities, mount policy, bootstrap profile, and later Python env policy.”

Remember: creating a new profile is policy work. Creating a new installer is execution work. Do not mix the two. 
# profiles.tsv decides account identity and role defaults

aiengineer    Researcher    labuser    labuser    Researcher    labuser    0    0    1    1    1    0    AI Engineer SMB profile

# mount-profiles.tsv decides enabled shares
research      0             0          1          1          1          0    Mount ingress, egress, and research shares

Why installers exist

Installers are trusted functions that can be audited, syntax-checked, allowlisted, and run one at a time. This avoids the common failure mode where a config file becomes a script and any typo or malicious value becomes executable.

Do not add executable shell to .env, .tsv, or .plan files. If it runs commands, it belongs in installers.sh and must be allowlisted in config.sh.

2. Account lifecycle scenario

Scenario. You need a new AI engineer, research scientist, or publisher account. You want the user, group, home permissions, SMB profile, mount profile, bootstrap profile, and target env file created consistently from one profile instead of manually building each piece.
Key insight. Account creation should produce an inspectable target policy before anything else. Dry-run first, then apply. Password setup is deliberately interactive unless explicitly handled through Linux tools such as passwd and chage.

Target account flow

sudo config --create-target --profile AIEngineer --name aiengineer --dry-run
sudo config --create-target --profile AIEngineer --name aiengineer --interactive

sudo config --create-target --profile ResearchScientist --name researchscientist --dry-run
sudo config --create-target --profile Publisher --name publisher --dry-run
What this code does. The dry-run commands resolve the selected target profile into a concrete account plan: Linux user, groups, home mode, target role, SMB profile, mount profile, bootstrap profile, and target env file path. The interactive command applies the plan only after confirmation. Use dry-run first when validating a new profile or a changed profile reader.

Operator account flow

sudo config --create-operator --profile DefaultOperator --name vmuser --dry-run
sudo config --create-operator --profile DefaultOperator --name vmuser --interactive
What this code does. These commands exercise the operator-account path. They should only accept profiles whose account_kind is operator. This path is intentionally separate from target creation because operator accounts can own or operate the configuration system itself.
Command intent. --create-target is for accounts that receive role-specific policy. --create-operator is for accounts that own or operate the tool. The selected profile kind must match the command kind.

Why these switches are runtime choices

Account creation mixes stable policy and one-time operator decisions. The profile decides stable things such as role, group, mount profile, SMB profile, and bootstrap profile. Switches decide runtime behavior: dry-run versus apply, prompt versus non-interactive execution, and whether password expiry should be applied now.

ChoiceShould be profile policy?Should be switch?Reason

Password and first-login expiry

# interactive create can ask whether to run passwd USER
sudo config --create-target --profile AIEngineer --name aiengineer --interactive

# expire at first login, after a password exists or was just set
sudo config --create-target --profile AIEngineer --name aiengineer --interactive --expire-password

# manual fallback
sudo passwd aiengineer
sudo chage -d 0 aiengineer
Expected behavior. Interactive mode can prompt to set a password. Non-interactive mode must not prompt and should print the later sudo passwd USER command. --expire-password should not run blindly if no password was set.

Removal workflow once the lifecycle tasks are implemented

sudo config --remove-target --name aiengineer --dry-run
sudo config --remove-target --name aiengineer --keep-home
sudo config --remove-target --name aiengineer --remove-home
sudo config --remove-target --name aiengineer --purge-config

sudo config --remove-operator --name oldoperator --dry-run
Removal rule. The safe default keeps home directories, state, target env files, and credentials. Destructive removal must be explicit.

3. Profile-kind validation scenario

Scenario. You accidentally run --create-operator with --profile AIEngineer. Without validation, the tool can produce a target policy from an operator command, which is misleading and dangerous.
Key insight. The command type is part of the contract. Operator commands must accept only operator profiles. Target commands must accept only target profiles. When there is a mismatch, the tool should fail and suggest valid profiles from accounts/profiles.tsv.
CommandValid profile kindValid examplesShould reject
create-operatoroperatorDefaultOperatorAIEngineer, ResearchScientist, Publisher, DefaultTarget
create-targettargetDefaultTarget, AIEngineer, ResearchScientist, PublisherDefaultOperator

What the validation code should do

The validation should run after config_resolve_account_profile has loaded the selected profile into ACCOUNT_PLAN_* variables, but before the plan is printed, reconciled, or applied. That placement matters: before resolution, the code does not know the profile kind; after apply, it is too late. 

config_resolve_account_profile "$resolved_profile" ...
config_validate_account_plan_kind "$kind" || return 1
config_print_account_plan_summary
config_print_account_plan_actions
Key note. This is not a cosmetic check. It protects the account lifecycle model. create-operator and create-target are different workflows, even if both eventually create Linux users.

Mismatch: operator command with target profile

config --create-operator --profile AIEngineer --name testengineer --dry-run --expire-password
What this code does. This is a negative test. It intentionally passes a target profile to the operator creation command. The correct behavior is to fail before printing or applying a plan, then suggest valid operator profiles from accounts/profiles.tsv.

Expected error shape:

[ERROR] Profile kind mismatch.
[ERROR] Command kind: operator
[ERROR] Profile AIEngineer has account_kind=target
[INFO] Use create-target for target profiles, or choose one of these operator profiles:
  - DefaultOperator

Mismatch: target command with operator profile

config --create-target --profile DefaultOperator --name testoperator --dry-run
What this code does. This is the opposite negative test. It proves that the target creation path rejects operator profiles. This prevents a developer from accidentally using operator policy to create an ordinary target account.

Expected error shape:

[ERROR] Profile kind mismatch.
[ERROR] Command kind: target

Implementation note. Do not hard-code the suggestions if possible. Read the valid profiles from accounts/profiles.tsv by filtering the second column, account_kind.

5. Python environment policy scenario

Scenario. You need one stable AI engineering environment, one stable research environment, one publishing environment, and temporary experiment environments. You do not want packages installed into base by accident, and you do not want the active shell environment to control managed installs silently.
Key insight. Functions are global; Python packages are environment-specific. The same managed step can be reused across roles, but it must print and use the resolved PYTHON_ENV.
Account profileAIEngineer
Target roleai-engineer
Python env profileaiengineer
Target envPYTHON_ENV=aiengineer
Installerpip install into aiengineer

What environment-aware installer code should do

A Python-installing function should resolve the target environment before installing anything. The preferred order is: explicit argument, then PYTHON_ENV from target policy, then a configured default. It should not use the currently active shell environment by accident. 

ResolveTargetPythonEnv:
  1. use explicit env argument if provided
  2. else use PYTHON_ENV from targets/USER.env
  3. else use CONFIG_PYTHON_ENV_DEFAULT if defined
  4. refuse system Python unless PYTHON_ENV_ALLOW_SYSTEM=1
  5. if env is missing and PYTHON_ENV_CREATE_MISSING=0, fail or skip clearly
Important note. base is not wrong when chosen intentionally. It is wrong when reached accidentally because no env was resolved.

6. AI platform development scenario

Scenario. You are building an AI-powered platform: API services, LLM tooling, model development utilities, MLOps scripts, and possibly Kubernetes or Runpod workflows. This should live in the stable aiengineer role environment, not in throwaway experiment envs.
Key insight. The AI platform environment should be boring and reproducible. Experimental package pins should be tested elsewhere before being promoted into the stable role env. 
# create/reconcile account
sudo config --create-target --profile AIEngineer --name aiengineer --dry-run
sudo config --create-target --profile AIEngineer --name aiengineer --interactive --expire-password

# inspect target policy
config --target aiengineer config-show

# create env manually if policy says create_missing=0
sudo -H -u aiengineer bash -lc 'conda create -n aiengineer python=3.11'

# install stable platform stacks one step at a time
sudo config --target aiengineer bootstrap step install_ml_base_python_stack
sudo config --target aiengineer bootstrap step install_llm_stack
sudo config --target aiengineer bootstrap step install_api_stack
sudo config --target aiengineer bootstrap step install_ml_dev_tools

# run platform code inside the env
sudo -H -u aiengineer bash -lc 'conda run -n aiengineer python -m uvicorn app:app --reload'
What this code does. This sequence creates the AI engineer target, checks its generated policy, creates the role's stable Python environment, then runs individual managed install steps. Each bootstrap step call should go through the plan/marker/allowlist system rather than directly invoking shell functions. The final command runs application code as the target user inside the resolved environment.

7. Parallel experiment scenario

Scenario. You want to test a new Torch build, a new Transformers version, or a model stack without risking the stable AI platform environment. You create a named experiment env and run the same managed step into that env explicitly.
Key insight. Experiment environments are allowed to be unstable. Stable role environments should not be. The difference is enforced by explicit PYTHON_ENV selection. 
# create isolated experiment env
sudo -H -u aiengineer bash -lc 'conda create -n torch-nightly python=3.11'

# override target/session policy
sudoedit /home/vmuser/.local/etc/config-sh/targets/aiengineer.env
# set: PYTHON_ENV="torch-nightly"

# run only relevant steps
sudo config --target aiengineer bootstrap step install_pytorch_stack
sudo config --target aiengineer bootstrap step check_pytorch_cuda

# verify
sudo -H -u aiengineer bash -lc 'conda run -n torch-nightly python -c "import torch; print(torch.__version__, torch.cuda.is_available())"'
After an experiment, either keep the env for reproducibility, delete it, or promote its package versions into role defaults if it becomes the new standard.

Scenario. You are running scientific exploration, simulation, parameter search, or GRN/Turing-pattern research. You need reliable scientific Python tooling, but you also want per-project environments for specific hypotheses or papers.
Key insight. Research tooling should be reproducible and separate from platform engineering. Project-specific environments prevent one paper or experiment from destabilizing the general research role.
