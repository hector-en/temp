Using your config shell tool

Abstract: where you are, what you are touching, and why the order matters

This tool is for the moment when you are logged in as Operator (vmuser) and need to configure a working account such as AI Engineer (AIEngineer), Research Scientist (ResearchScientist), or Publisher. The first question is not “what command exists?” but “who will this affect, and at what scope?”

The safe workflow is always the same: create missing templates once with config config-init, inspect the target with config-show, inspect the step registry with bootstrap steps, inspect target state with bootstrap status, allow only the step you mean to run, then run one selected step with bootstrap step STEP.

If the flow is not followed, common mistakes are predictable: files land under the wrong home directory, target-owned files become root-owned, a system-wide installer runs when you only meant to configure one role, or a plan/profile edit does not affect an already-created target plan. The guide below keeps those boundaries visible.

The style is deliberately companion-like: every topic says where the operator is, what to do, why the command matters, and which files carry policy, state, or executable behavior.

1. Architecture map before commands

MapFlowBoundarySummary

What this flow achieves

The architecture separates decisions from execution. Policy files say what a role should prefer. The plan says what a target is currently allowed to run. The engine validates and dispatches. The installer library contains trusted executable behavior. Runtime markers remember what already happened.

bin/config.sh

Engine: target parsing, config loading, state, safety, allowlist, dispatch.

config --target AIEngineer bootstrap step STEP
# config.sh validates target, plan, marker, function allowlist

2. Before you run anything

config-initTargetInspectEdit locationExecution boundary

Initialize templates only when needed

ContextYou use config config-init when the shared editable configuration layout is missing or after the tool gained new template files. It is not a per-target daily command.
Do
config config-init
WhyIt creates commented shared files under /home/vmuser/.local/etc/config-sh. Normal safe behavior is create-if-missing, not overwrite-existing. Use bootstrap plan-init, not config-init, when creating a target’s runtime checklist.
Why not config --target AIEngineer config-init? Because the templates are shared tool policy. The target-specific runtime file is AIEngineer’s bootstrap.plan, created with sudo config --target AIEngineer bootstrap plan-init.

Sticky command note

config config-init

Create missing shared templates. Run once after install, after template changes, or to repair missing files. It should not overwrite existing files in normal use. It does not create a target user; it prepares shared policy files.

Start from where you are

ContextYou are usually logged in as Operator (vmuser), but you may be configuring AI Engineer (AIEngineer). The first question is not “what command exists?” but “who will this affect?”
Do
config --target AIEngineer status
sudo config --target AIEngineer bootstrap status
WhyThe target controls TARGET_HOME, STATE_DIR, target config, mount identity, and the bootstrap plan path.

Sticky command note

--target AIEngineer

All target-sensitive logic follows this identity. If you omit or mistype it, you may inspect or change the wrong account.

Inspect before changing

ContextIf you are unsure what the tool will do, stay in inspection mode first.
Do
config --target AIEngineer config-show
config --target AIEngineer bootstrap steps
sudo config --target AIEngineer bootstrap status
WhyThese commands explain loaded policy, available steps, and current target state without installing packages or mounting shares.

Sticky command note

Inspection trio

config-show explains policy. bootstrap steps explains the registry. bootstrap status explains current runtime state.

Choose the right edit location

ContextYou may be changing a use case, a package list, a step definition, or real behavior. Those are different types of edits.
Do
  • Edit etc/config-sh/targets/USER.env for user policy.
  • Edit etc/config-sh/install/*.env for packages, versions, and repo metadata.
  • Edit etc/config-sh/bootstrap/steps.tsv to register step metadata.
  • Edit lib/config-sh/installers.sh for actual installer behavior.
  • Edit bin/config.sh for engine behavior, dispatch safety, or allowlist changes.

Sticky command note

Rule

If it is a value, prefer etc. If it runs shell commands, it belongs in trusted source. If it records what happened, it belongs in state.

Know when you cross into execution

ContextA command can be safe, state-changing, or execution-heavy.
Do
# Safe
config --target AIEngineer config-show

# State-changing
sudo config --target AIEngineer unskip STEP

# Execution
sudo config --target AIEngineer bootstrap step STEP
Whybootstrap step can run an installer. Broad bootstrap can run many installers.

Sticky command note

Execution boundary

Use status/steps first. Prefer one-step execution until the target plan is trustworthy.

3. Configure all target roles

Naming note: if your Linux system allows uppercase usernames, you can use AIEngineer, ResearchScientist, and Publisher. For maximum shell portability, lowercase equivalents are safer. The guide uses the requested role labels.

Operator (vmuser)

Download Codex target-prep instructions

ContextThis is the admin/operator account that owns the tool and performs system-level orchestration. It should be able to inspect, mount, pull/push, and manage target plans.
Policy file/home/vmuser/.local/etc/config-sh/targets/vmuser.env
Do
TARGET_ROLE="operator"
TARGET_ROLE_LABEL="Operator"
BOOTSTRAP_PROFILE="operator"
SYNC_SYSTEM_ITEMS="1"
SMB_USER_DEFAULT="hector"

Variable sticky note

TARGET_ROLE

Machine-friendly policy key. It does not have to be a Linux username. Use it to group behavior such as ai-engineer, research-scientist, or publisher.

TARGET_ROLE_LABEL

Human-readable label for help text, guides, and future reporting. It is just a label unless your code later chooses to display it.

BOOTSTRAP_PROFILE

Name of the profile template used by bootstrap plan-init when the target plan is missing. It should correspond to a file under etc/config-sh/bootstrap/profiles/.

SYNC_SYSTEM_ITEMS

0 means user/target-scoped sync only. 1 allows supported system-level sync and should normally be reserved for Operator (vmuser).

SMB_USER_DEFAULT

Default SMB username for mounts/sync identity when no command-specific override is provided. It is not a password and should not store secrets.

WhyThe operator profile can include administrative/system-capable steps because this account manages the workstation and shared tool layout.
Likely installers

System basics, networking, mount support, Docker/system tooling if used for administration, config sync tooling, shell helpers. Avoid user-specific research stacks here unless Operator (vmuser) also uses them directly.

4. Use-case scenarios

Run one stepChange packagesReset state

Run one selected step

ContextYou know the step you want, but you do not want broad bootstrap. This is the normal safe execution path.
Do
config --target AIEngineer bootstrap steps
sudo config --target AIEngineer unskip install_kubernets
sudo config --target AIEngineer bootstrap status
sudo config --target AIEngineer bootstrap step install_kubernets
WhyIt verifies the registry, opens only the intended gate, checks runtime state, then runs one trusted function.

Sticky command note

bootstrap step STEP

One-step execution. Prefer this until the whole plan is trustworthy.

Change packages for an existing installer

ContextYou are changing input to an existing installer, not adding new behavior.
Do
sudoedit /home/vmuser/.local/etc/config-sh/install/packages.env
sudo config --target ResearchScientist bootstrap status
sudo config --target ResearchScientist bootstrap step install_dev_env_python_user_tools
WhyEditing packages.env does not change system state. The step changes state only when executed.

Sticky command note

packages.env

Configuration input, not execution. It becomes active only when an installer reads it.

Clear state but keep safe

ContextA step is done or failed, but you want to reset it without making it surprise-run.
Do
sudo config --target AIEngineer rm install_minikube
sudo config --target AIEngineer bootstrap status
Whyrm clears runtime state and should leave the plan skipped. unskip is the later explicit allow signal.

Sticky command note

rm STEP

Reset state while preserving safety. It is not the same as run again.

6. Policy and env files: gravity and effect

Gravity rule: editing an .env file changes future command inputs. It does not install packages, copy files, or change system state until an execution command consumes those values.
FileAffectsImmediate system state?
targets/USER.envRole, profile, SMB defaults, sync breadth.No.
install/packages.envPackage groups consumed by installers.No.
install/versions.envVersion strings and installer filenames.No.
bootstrap/steps.tsvStep metadata and function mapping.No, but it can affect dispatch if function is allowlisted.
state/config-sh/bootstrap.planCurrent target allow/block decisions.State-changing, but not installer execution by itself.

8. Add a new installer

ContextYou are adding executable behavior. That means source code plus trust plus registry plus target intent.
Do
# 1. Add trusted function in installers.sh
InstallNodeJS() {
  config_apt_refresh_if_stale || return 1
  config_apt_install_list APT_NODEJS "nodejs npm" || return 1
}

# 2. Add package group in packages.env
APT_NODEJS="nodejs npm"

# 3. Add InstallNodeJS to config_bootstrap_function_allowed in config.sh

# 4. Register in steps.tsv
install_nodejs    InstallNodeJS    system    1    Install Node.js and npm

# 5. Choose profile default
skipped install_nodejs
WhySource code creates capability, allowlist grants trust, manifest registers metadata, profile/plan decides whether it runs.

Sticky command note

After editing source
bash --noprofile --norc -n /home/vmuser/.local/lib/config-sh/installers.sh
bash --noprofile --norc -n /home/vmuser/.local/bin/config.sh
After registering
config --target AIEngineer bootstrap steps

11. Troubleshooting by symptom

The step does not run and says skipped by plan
sudo config --target AIEngineer unskip STEP
sudo config --target AIEngineer bootstrap status
sudo config --target AIEngineer bootstrap step STEP
The step does not run and says already done
sudo config --target AIEngineer rm STEP
sudo config --target AIEngineer unskip STEP
sudo config --target AIEngineer bootstrap step STEP
I added a row to steps.tsv but the step is unknown
  1. Confirm the function exists in installers.sh.
  2. Confirm it is in config_bootstrap_function_allowed.
  3. Confirm steps.tsv uses the exact same function name.
  4. Run config --target AIEngineer bootstrap steps.
