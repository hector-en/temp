2. Daily loop

Safe workflow

  1. Name the step: install_example_tooling.
  2. Name the function: InstallExampleTooling.
  3. Add implementation to installers.sh.
  4. Add allowlist mapping in config.sh.
  5. Add a row to bootstrap/steps.tsv.
  6. Add profile plan rows for the right roles.
  7. Add package/repo defaults if needed.
  8. Run syntax checks only.
  9. Inspect target plans.
  10. Unskip and run one step only.

Avoid

  • Do not put shell code into *.env, *.tsv, or *.plan.
  • Do not use eval for config-driven execution.
  • Do not run full bootstrap just to validate one function.
  • Do not read or print credential files.
  • Do not store secrets, tokens, research data, or vault contents in config files.

3. Add the trusted function

New executable work should be a shell function in installers.sh. It should be idempotent: running it twice should not corrupt the target.

Target context: use TARGET_USER, TARGET_HOME, CURRENT_HOME, and config defaults loaded from etc/config-sh/install/*.env. Do not assume the user is always labuser.
InstallExampleTooling() {
  local target_user="${TARGET_USER:-}"
  local target_home="${TARGET_HOME:-}"

  if [ -z "$target_user" ] || [ -z "$target_home" ]; then
    echo "[ERROR] TARGET_USER/TARGET_HOME not set" >&2
    return 1
  fi

  echo "[INFO] Installing example tooling for ${target_user}"
  install -d -m 755 -o "$target_user" -g "$target_user" "${target_home}/.local/bin"

  if [ -z "${EXAMPLE_TOOLING_REPO_URL:-}" ]; then
    echo "[SKIP] EXAMPLE_TOOLING_REPO_URL is empty"
    return 0
  fi

  # Narrow, explicit work goes here.
}
  • Use target context, not hard-coded usernames.
  • Do not print secrets.
  • Skip clearly when optional config is missing.
  • Create target-owned files with explicit owner/mode.
  • Return non-zero only for real failures.

4. Register the step

Allowlist in config.sh

install_example_tooling)

  ;;

Step registry row

Use the exact column order already present in your steps.tsv.

No arbitrary dispatch: a step from a plan must map to a known trusted function, or it should fail/skip safely.

6. Refresh targets and plans

Account profiles and target env files describe who the user is. Bootstrap profile plans describe what the user can receive. The runtime target plan is what execution uses.

config --target aiengineer config-show
config --target aiengineer bootstrap steps
sudo config --target aiengineer bootstrap status
  1. Add the step to the role profile plan.
  2. Refresh/reconcile the target plan using your existing plan-aware command.
  3. Inspect the target plan/status.
  4. Unskip only the step you intend to run.
Target env files: files under /home/vmuser/.local/etc/config-sh/targets should remain operator-owned policy files, for example vmuser:operator with mode 600.

# installers.sh
InstallExamplePythonTools() {
  local packages="${PIP_EXAMPLE_TOOLS:-}"
  if [ -z "$packages" ]; then
    echo "[SKIP] PIP_EXAMPLE_TOOLS is empty"
    return 0
  fi
  echo "[INFO] Installing Python tools for ${TARGET_USER}"
  sudo -H -u "$TARGET_USER" python3 -m pip install --user $packages
}

11. Commit checklist

Before commit

  • Function added to installers.sh.
  • Step allowlisted in config.sh.
  • Step row added to steps.tsv.
  • Profile rows added only where appropriate.
  • Package/repo defaults added if needed.
  • Syntax checks passed.
  • No secrets or private data printed.
