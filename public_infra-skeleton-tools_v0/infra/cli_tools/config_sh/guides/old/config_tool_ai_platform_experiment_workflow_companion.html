1. What this gives you day to day

The point is not just isolation. The point is repeatable role setup: you declare which environment a role or experiment should use, then the same managed functions install/check the right tools in the right place every time.

AI platform work

Stable platform environment for FastAPI, LLM tools, ML base packages, Kubernetes checks, Runpod tools, and agent workspace code.

PYTHON_ENV="aiengineer"

Experiments

Temporary or project-specific environments for package versions you do not want to leak into the stable platform env.

PYTHON_ENV="experiment1"

Research

Separate environment for research/numerics/GRN/parameter-search tooling, independent from AI platform dependencies.

PYTHON_ENV="researchscientist"

With manual installs, you remember commands and hope you are in the right env. With this workflow, the target profile says which env to use, the install function prints what it is doing, and the plan/state system records what was applied.

3. Why this is better than manual installs

Daily problemManual install habitManaged profile/env workflow
Wrong env You activate an env manually and hope it is the right one. PYTHON_ENV is resolved from the target/profile and printed before install.
Reproducibility Commands live in shell history or notes. Package sets live in operator-owned config defaults and managed functions.
Parallel experiments New package pins can accidentally contaminate base. Override to experiment1 for one target/step.
Role setup You remember different commands for AI, research, and publisher roles. Each profile has planned steps and default env policy.
Audit trail You have no consistent record of what ran. Bootstrap plan and state markers record pending/done/skipped/failed.
Safety sudo pip or system Python mistakes can break shared Python. System Python is blocked unless explicitly allowed.
Manual installs are still possible. The managed workflow is for repeatable role setup and stable operations. For a one-off throwaway test, manual may be fine. For anything you expect to repeat, promote it into a managed function and profile/env policy.

ResearchScientist   research-scientist   researchscientist   auto         0               0             Research and simulation tooling

When a target is reconciled, its target env should contain:

PYTHON_ENV_PROFILE="AIEngineer"
PYTHON_ENV="aiengineer"
PYTHON_ENV_MANAGER="auto"
PYTHON_ENV_CREATE_MISSING="0"
PYTHON_ENV_ALLOW_SYSTEM="0"

5. Daily workflows

Normal role setup

# see policy
config --target aiengineer config-show

# create env manually if needed
sudo -H -u aiengineer bash -lc 'conda create -n aiengineer python=3.11'

# run one managed step
sudo config --target aiengineer bootstrap step install_ml_base_python_stack

# verify inside env
sudo -H -u aiengineer bash -lc 'conda run -n aiengineer python -c "import numpy; print(numpy.__version__)"'

Experiment setup

# create experiment env
sudo -H -u aiengineer bash -lc 'conda create -n experiment1 python=3.11'

# override target env policy
sudoedit /home/vmuser/.local/etc/config-sh/targets/aiengineer.env
# set: PYTHON_ENV="experiment1"

# run same managed step into experiment1
sudo config --target aiengineer bootstrap step install_pytorch_stack

# compare with stable env
sudo -H -u aiengineer bash -lc 'conda run -n experiment1 python -c "import torch; print(torch.__version__)"'

6. AI platform workflow

Use the stable aiengineer env for platform services and reusable AI engineering tooling.

# target policy should resolve to aiengineer
config --target aiengineer config-show

# setup stable platform packages
sudo config --target aiengineer bootstrap step install_ml_base_python_stack
sudo config --target aiengineer bootstrap step install_llm_stack
sudo config --target aiengineer bootstrap step install_api_stack
sudo config --target aiengineer bootstrap step install_ml_dev_tools

# run platform code inside the env
sudo -H -u aiengineer bash -lc 'conda run -n aiengineer python -m uvicorn app:app --reload'
Benefit: your API/LLM/MLOps platform has a known stable dependency set. Experiments do not mutate it unless you explicitly target this env.

7. Experiment workflow

Use experiment envs when testing package versions, model stacks, GPU builds, or research hypotheses.

# create isolated experiment env
sudo -H -u aiengineer bash -lc 'conda create -n torch-nightly python=3.11'

# override for this target/session policy
sudoedit /home/vmuser/.local/etc/config-sh/targets/aiengineer.env
# set: PYTHON_ENV="torch-nightly"

# run only the relevant step
sudo config --target aiengineer bootstrap step install_pytorch_stack
sudo config --target aiengineer bootstrap step check_pytorch_cuda

# verify experiment env
sudo -H -u aiengineer bash -lc 'conda run -n torch-nightly python -c "import torch; print(torch.__version__, torch.cuda.is_available())"'
After the experiment: either keep the env for reproducibility, delete it, or promote its package versions into the role default config if it becomes the new standard.

8. Research workflow

Use researchscientist for stable research tooling, and separate experiment envs for paper-specific or hypothesis-specific runs.

# stable research tooling
config --target researchscientist config-show
sudo config --target researchscientist bootstrap step install_grn_research_python_stack
sudo config --target researchscientist bootstrap step install_parameter_search_tooling

# project-specific experiment env
sudo -H -u researchscientist bash -lc 'conda create -n grn-exp-a python=3.11'

# override only this target policy if needed
sudoedit /home/vmuser/.local/etc/config-sh/targets/researchscientist.env
# set: PYTHON_ENV="grn-exp-a"

# run research stack into that env
sudo config --target researchscientist bootstrap step install_grn_research_python_stack
Do not put raw research data, unpublished datasets, or manuscript text into config files or postcheck logs. The env policy should reference tooling, not private content.

9. Publisher workflow

Use publisher for notebook/export/publishing Python tools. Keep manuscript/vault content out of the config system.

config --target publisher config-show

sudo config --target publisher bootstrap step install_publisher_base_tools
sudo config --target publisher bootstrap step install_pandoc_obsidian_tools

# verify publishing Python tools
sudo -H -u publisher bash -lc 'conda run -n publisher python -m pip list'

10. Common command recipes

Inspect env policy

config --target aiengineer config-show | grep -E 'PYTHON_ENV|TARGET_ROLE|ACCOUNT_PROFILE'
config --target researchscientist config-show | grep -E 'PYTHON_ENV|TARGET_ROLE|ACCOUNT_PROFILE'
config --target publisher config-show | grep -E 'PYTHON_ENV|TARGET_ROLE|ACCOUNT_PROFILE'

List conda envs as a target user

sudo -H -u aiengineer bash -lc 'conda env list'
sudo -H -u researchscientist bash -lc 'conda env list'
sudo -H -u publisher bash -lc 'conda env list'

Check imports in a specific env

sudo -H -u aiengineer bash -lc 'conda run -n aiengineer python -c "import fastapi, transformers; print("ok")"'
sudo -H -u researchscientist bash -lc 'conda run -n researchscientist python -c "import numpy, scipy; print("ok")"'
sudo -H -u publisher bash -lc 'conda run -n publisher python -c "import nbconvert; print("ok")"'

Promote an experiment to the default role env

# Example decision after experiment1 works:
# 1. update package/version defaults
sudoedit /home/vmuser/.local/etc/config-sh/install/packages.env

# 2. set role env back to stable env if needed
sudoedit /home/vmuser/.local/etc/config-sh/targets/aiengineer.env
# PYTHON_ENV="aiengineer"

# 3. run the managed step into stable env
sudo config --target aiengineer bootstrap step install_pytorch_stack

11. Troubleshooting

ProblemWhy it happensWhat to do
I installed a package but import failsIt was installed into another envCheck PYTHON_ENV and run import test inside that exact env.
Experiment broke my platformExperiment packages were installed into stable envUse PYTHON_ENV=experiment1 before running experimental steps.
Installer wants system PythonEnv resolution failed or policy allowed fallbackKeep PYTHON_ENV_ALLOW_SYSTEM=0 and set PYTHON_ENV explicitly.
Env is missingcreate_missing=0Create env manually, or deliberately set create_missing=1.
Wrong target got packagesCommand used wrong --targetAlways inspect config --target USER config-show first.
Manual install driftAd-hoc command was never promoted into configAdd package to defaults and route install through a managed step.
Rule of thumb: manual for throwaway tests, managed step for anything repeatable.
